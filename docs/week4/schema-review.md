# Schema self-review
 
1. **Works well:** Every requirement that stores data has a table or column in schema.md (2a): FR-01 to FR-03, FR-05 to FR-07, FR-09 to FR-14 and FR-17 are covered, and FR-15, FR-16 and FR-18 to FR-21 are marked Later. The requester tasks (submit, see my place, cancel) and the staff tasks (print next, mark ready, mark done, open the PDF) all have the data they need. **Problem (question 1):** `tickets` had five timestamps (`created_at`, `printing_at`, `ready_at`, `completed_at`, `cancelled_at`), but no requirement mentions a time. FR-05, FR-07, FR-09 and FR-10 only say that the status changes, and only `created_at` is needed, for the queue order. Also, `completed_at` and `cancelled_at` are two columns for one fact, the time a ticket ended, and a ticket ends only one way, so one of them was always empty. **Change:** I merged `completed_at` and `cancelled_at` into one `finished_at`, and the status says whether the ticket was done or cancelled. I kept `printing_at`, `ready_at` and `finished_at` even though no requirement asks for them, because each is a fact the database can record when the status changes, and they cannot be rebuilt later. Each has a check so it cannot be before `created_at`. I wrote this reason in schema.md (2c) and updated 2a, 2b and the ERD.
2. **Works well:** A ticket stores only `user_id`, so the person's name is kept in `users` and not copied into every ticket. **Problem (question 2):** One `name` column cannot tell a first name from a last name, so the same person could be saved twice with the name typed in a different order. **Change:** I split `users.name` into `first_name` and `last_name`, with a `UNIQUE (first_name, last_name)` constraint in schema.md (2c). Neither column is unique alone, because many people share a first name or a last name, but the pair is. In this project, the app assumes that no two people share the same first and last name together in this scope, so the pair identifies one person. Flask will find the user by the pair and reuse that row, and fix the capitalization before saving.
3. **Works well:** Each column has a type that fits its data, with `timestamptz` for times and `text` for the free-form notes. **Problem (question 6):** A `text` column has no length limit. Flask limits the notes to 300 characters on the form, but a request that skips the form could send much more. **Change:** I kept `CHECK (notes IS NULL OR length(notes) <= 300)` on `tickets.notes` and wrote the reason in schema.md (2c).
4. **Works well:** Both foreign keys use `RESTRICT`, so a service or user with tickets can never be deleted by accident. **Problem (question 5):** When staff permanently delete a request (FR-13), the ticket row goes but the PDF may still be on disk. **Change:** I wrote in schema.md (2a and 2c notes) that the application deletes the PDF first and then the ticket. The user row is kept, because the same person may have other tickets.
